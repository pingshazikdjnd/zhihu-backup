## 三、关键结论

### 1. 永远拿不到的字段（include 也无效）

| `voteup_count` / `favorite_count` / `visit_count` / `thanks_count` | 回答列表 | proj/max 两轮 include 均被忽略，返回体里没有这些键 |
| `favorite_count` | 回答详情 | detail_inc 请求了 index 也没有，真实收藏数在 `reaction.statistics.favorites` |

### 3. include 语法陷阱（实测）

- 只有 **首项带 `data[*].` 前缀 + 逗号编码成 `%2C`** 才生效；
- 如果写成“原始逗号 + 每项都重复 `data[*].` 前缀”，服务端会**整体静默忽略**整串 include（连 `comment_count`/`content` 都不返回），且不会报错。
- `collections/{id}/items` 与评论接口**整体忽略 include**，请求了也不影响返回。
- `collections/{id}/items` 使用 `limit=50` 会静默返回 `totals=0 / data=[]`，`limit=20` 正常；采集翻页建议 ≤20。

### 4. 评论接口的真实字段名（与代码假设不同）

| 代码/直觉 | 真实字段 | 说明 |
|---|---|---|
| `likes` / `like_count` | **`vote_count`** | 评论点赞数 |
| `is_top` / `is_featured` | **`top` / `featured`** | 布尔键名无 is_ 前缀 |
| `img_url` | **不存在** | 图片信息在 `attached_info`（不透明字符串） |
| `author.name` | **`author.member.name`** | 评论 author 是 `{role, member{...}}` 两层 |

### 5. 各接口形态差异（同一实体字段不通用）

- **answer**：列表 38 键（带 include）/详情 90 字段/收藏夹 27 键/动态 target 34 键/推荐流 32 键 —— 5 套形态，`reaction.statistics` 只有详情是 17 键全量，列表只有 `{like_count, favorites}`。
- **author**：11 个上下文里 61 个键无任何两组完全一致；`followers_count` vs `follower_count` 两种命名并存。
- **article**：列表 25 键 / 收藏夹形态 14 键 / 专栏详情 69 键；时间字段列表用 `created/updated`，收藏夹也一样，而 answer 用 `created_time/updated_time`。
- **question**：直连 `/api/v4/questions/{id}` 实测 403/10003（缺 x-zse-96 签名），只能从动态/热榜内嵌拿 16~31 字段。
- **pin（想法）**：本次窗口未出现 pin 类型，`/api/v4/pins/{id}` 未验证成功；`votes`/`upvotes` 端点因 403 停止规则未测到。
